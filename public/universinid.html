0.1 SDD — Spec-Driven Development

O que é SDD e por que o NID adotou como padrão de trabalho com IA

Resumo

SDD (Spec-Driven Development) é o ciclo de trabalho central do NID: primeiro você especifica o que quer, depois o agente planeja como fazer, e só então implementa. Isso elimina o maior desperdício do trabalho com IA — retrabalho por ambiguidade.

O problema que SDD resolve

Sem SDD, o fluxo típico com IA é:

"Faz uma medida DAX de faturamento" → IA entrega algo → "não era isso" → retrabalho

Com SDD, o fluxo é:

/nid:specify → spec aprovada → /nid:plan → plano aprovado → /nid:gate → GO → /nid:implement

A aprovação em cada etapa é humana e explícita. O agente não avança sozinho.

As 5 fases do ciclo NID

Fase Comando O que acontece Aprovação humana
1. Especificação /nid:specify Brainstorm → spec aprovada ✅ Obrigatória
2. Planejamento /nid:plan Spec → plano técnico detalhado ✅ Obrigatória
3. Tasks /nid:tasks Plano → lista de tarefas com critérios ✅ (implícita via /nid:gate)
4. Gate /nid:gate Red-team adversarial — STOP-SHIP / GO ✅ Bloqueante
5. Implementação /nid:implement Execução das tasks com verificação — (agente executa)

Nota: Em modo Casual, você pode pular as fases formais. SDD completo é opcional — só obrigatório em projetos Formal (com /nid:init).

Por que "Spec antes de código"?

LLMs são excelentes executores mas péssimos leitores de mente. Quanto mais claro o O QUE, melhor o COMO. A spec funciona como contrato entre você (humano) e o agente.

Custo de ambiguidade:

  • Spec ambígua → plano errado → código errado → retrabalho total
  • Spec clara → plano correto → código correto → revisão mínima

Modo Casual vs Formal

  • Casual: você usa skills e agentes sem /nid:init. Sem fases obrigatórias. Ótimo para tarefas pontuais.
  • Formal: projeto tem .claude/nid-project.json. Ciclo SDD completo. Hooks ativos.

A maioria do trabalho do NID hoje é Casual. Formal é para projetos maiores que precisam de rastreabilidade.

0.2 LLM — O que é e como usar bem

Como LLMs funcionam na prática e o que saber para trabalhar bem com eles

Resumo

Um LLM (Large Language Model) é um modelo de linguagem treinado para prever o próximo token. Isso soa simples, mas o resultado é uma ferramenta que, usada com disciplina, acelera drasticamente o trabalho técnico. Saber suas limitações é tão importante quanto saber seus pontos fortes.

Como o LLM "pensa"

O modelo não "entende" — ele prediz. Cada resposta é a sequência de tokens mais provável dado o contexto. Isso implica:

  • Alucinação: quando não sabe, inventa com confiança. Sempre verifique fatos
  • Context window: o modelo só vê o que está na janela de contexto ativa
  • Não tem memória entre sessões: sem ferramentas de memória, o modelo começa do zero
  • Segue instruções, não lê mente: quanto mais claro o prompt, melhor o resultado

O que LLMs fazem bem

Tarefa Por quê funciona bem
Gerar código boilerplate Padrões repetitivos → alta probabilidade
Revisar e refatorar código Análise de padrões no contexto
Escrever documentação Síntese de informação estruturada
Traduzir entre linguagens/formatos Mapeamento de padrões
Brainstorm de soluções Geração de variações plausíveis
Responder perguntas com contexto dado Inferência sobre contexto explícito

O que LLMs fazem mal (sem ferramentas)

  • Cálculos precisos: erros em aritmética complexa — use código
  • Datas e eventos recentes: data de corte do treinamento
  • Regras de negócio DELP específicas: não sabe o que não está no contexto — use knowledge/
  • Estado mutable: o modelo não sabe o que mudou desde o início da sessão sem ferramentas
  • Consistência em longo prazo: degrada em contextos muito longos

Claude Code e o NID

O NID usa Claude Code (CLI do Claude) como plataforma principal. Claude Code adiciona:

  • Ferramentas: Read, Edit, Write, Bash — o agente atua no sistema de arquivos real
  • Skills: instruções especializadas carregadas sob demanda (este kit)
  • Agentes: personas especializadas para cada domínio (BI, ETL, Azure, etc.)
  • Memória via arquivos: knowledge/ e CLAUDE.md fornecem contexto persistente

Princípio NID #2: sempre responde em pt-BR. Código e identifiers ficam em inglês quando a stack pede.

Calibrando confiança

Use esta heurística ao receber output de um agente:

Fato sobre o mundo real DELP? → Verifique na fonte (knowledge/, doc Microsoft, etc.)
Código gerado? → Rode e teste
Arquitetura proposta? → /nid:gate antes de implementar
Texto/documentação? → Revise antes de publicar

⚠️ O agente NID segue o Princípio #5: se não sabe, declara [PENDENTE] e propõe SIT (Solicitação de Informação Técnica). Nunca inventa dado do mundo real DELP.

0.3 Agent Orchestration — como agentes trabalham juntos

Como o NID usa múltiplos agentes especializados em paralelo ou em sequência

Resumo

Um único LLM generalista é bom em muitas coisas, mas agentes especializados são melhores em tarefas específicas. Orquestração de agentes é o padrão de despachar trabalho para especialistas (subagentes) e consolidar os resultados — parecido com delegar para uma equipe.

Analogia: equipe de desenvolvimento

Você (PO)
  └─ nid-tech-lead (orquestrador)
        ├─ nid-bi-engineer      → cria medidas DAX
        ├─ nid-data-engineer    → monta pipeline ETL
        └─ nid-code-reviewer    → revisa os dois

O nid-tech-lead não faz o trabalho — ele planeja, delega e consolida. Você só fala com ele.

Padrões de orquestração do NID

Padrão 1 — Sequencial (pipeline)

Cada agente recebe o output do anterior:

nid-product-manager → [spec] → nid-architect → [plano] → nid-tech-lead → [tasks] → agentes verticais

Quando usar: ciclo SDD formal, quando cada etapa depende da anterior.

Padrão 2 — Paralelo (tarefas independentes)

Agentes rodam ao mesmo tempo, sem dependência entre si:

nid-bi-engineer (medidas DAX) ─┐
nid-data-engineer (ETL)       ─┼→ nid-tech-lead consolida
nid-documentation-engineer    ─┘

Quando usar: quando as tarefas não se bloqueiam mutuamente. Economiza tempo.

Padrão 3 — Red-team (adversarial)

Um agente tenta quebrar o que outro fez:

nid-architect [proposta] → nid-red-team [critica adversarialmente] → GO ou REWORK

Quando usar: /nid:gate antes de qualquer implementação de projeto formal.

Por que o NID usa agentes especializados?

  • Contexto otimizado: cada agente tem system prompt focado no domínio (BI, Azure, ETL...)
  • Menos alucinação: especialista em DAX erra menos em DAX do que generalista
  • Escalabilidade: tarefas independentes rodam em paralelo
  • Rastreabilidade: qual agente fez o quê fica claro no log

Categoria Agentes Papel
Orchestration (4) architect, chief-of-staff, product-manager, tech-lead Planejamento e coordenação
Quality (8) code-reviewer, qa-engineer, red-team, tdd-coach, security-engineer, performance-engineer, accessibility-engineer, silent-failure-hunter Qualidade e segurança
Support (5) debugger, code-explorer, refactor-cleaner, documentation-engineer, prompt-curator Apoio ao desenvolvimento

0.4 Por que o NID adotou IA agêntica

O contexto e motivação por trás da adoção de IA agêntica no NID DELP

Resumo

O NID (Núcleo de Inovação DELP) gerencia um portfólio heterogêneo — BI/DAX, ETL Python, automações, Azure, M365, web apps MES, propostas técnicas. Antes do nid-spec-kit, cada projeto começava do zero. A adoção de IA agêntica com disciplina SDD resolve três problemas reais: acúmulo de conhecimento, onboarding e velocidade.

O portfólio NID antes do kit

ApontDELP (MES web)      → 18 agentes próprios em silo
Equipe Field (propostas) → 8 agentes próprios em silo
BI/DAX                   → sem padronização
ETL Python               → sem padronização
Azure AI/Data            → sem padronização
M365 Power Platform      → sem padronização

Cada projeto tinha sua própria abordagem — ou nenhuma. Novo dev NID levava semanas para entender as convenções. Conhecimento ficava na cabeça das pessoas, não em knowledge/.

Os 3 problemas que o kit resolve

1. Amnésia técnica

Quando um dev DELP aprende "usar Managed Identity + Key Vault no Azure" depois de horas de debugging, esse conhecimento sumia ao fechar a sessão. Com o kit:

  • Aprendizado → skill nid-azure-bicep-foundations (commitada)
  • Próxima vez → agente já sabe, não repete o debugging

2. Onboarding lento

Novo dev NID precisava de dias para entender o stack, convenções e ferramentas. Com o UniversiNID (este HTML) + o kit:

  • 5 módulos de capacitação estruturada
  • Skills documentadas e executáveis

3. Velocidade inconsistente

Sem padrão, cada dev resolve o mesmo problema de forma diferente. Com o kit:

  • Skill nid-etl-dim-fato define o padrão de modelagem Kimball para todo NID
  • Skill nid-dax-medidas define naming e time intelligence DAX
  • Próximo projeto começa no "ombro de gigantes", não do zero

Por que Claude Code especificamente

Claude Code (CLI do Claude) foi escolhido por:

  • Ferramentas de arquivo: Read, Edit, Write, Bash — atua no repo real
  • Skills carregáveis: SKILL.md + references/ — instruções modulares
  • Plugin system: plugin.json → kit instalável como dependência
  • Agentes com subagents: paralelismo real para tarefas independentes
  • Windows-first: equipe DELP usa Windows; Claude Code funciona bem no PowerShell

Resultado esperado

dev DELP abre Claude Code em qualquer projeto NID
    → kit instalado globalmente
    → agentes disponíveis
    → "use a skill nid-dax-medidas" → IA especialista em DAX DELP
    → conhecimento acumulado, não reinventado

0.5 Glossário Visual

Termos chave do universo NID com definições visuais e analogias

Resumo

Referência rápida dos termos do kit. Use como consulta quando encontrar uma palavra desconhecida.

Termos do Kit

nid-spec-kit

O plugin Claude Code que centraliza todos os agentes, skills, comandos e knowledge do NID. Instalado uma vez, disponível em qualquer projeto.

Skill

Instrumento de instrução especializada para o LLM. Estrutura: SKILL.md (regras + quando usar) + references/ (conteúdo profundo, carregado sob demanda). Análogo a um manual de procedimento operacional.

skills/
└── bi/
    └── nid-dax-medidas/
        ├── SKILL.md         ← lido sempre
        └── references/      ← lido só quando necessário

Agente (nid-*)

Persona especializada com system prompt focado em um domínio. O agente usa skills, mas tem papel próprio. Analogia: nid-bi-engineer é o "dev de BI especialista"; nid-dax-medidas é o manual que ele usa.

SDD (Spec-Driven Development)

Ciclo de trabalho: Especificar → Planejar → Gate → Implementar. Impede implementação sem aprovação humana em cada fase. Ver 0.1.

Gate (/nid:gate)

Checkpoint bloqueante entre planejamento e implementação. O nid-red-team ataca o plano; você decide GO ou NO-GO. Sem gate, sem /nid:implement em projetos formais.

Knowledge Base (knowledge/)

Diretório versionado com fatos DELP que o agente precisa mas não pode inventar: portfólio atual, ferramentas homologadas, regras de negócio, glossário, lições aprendidas. O agente lê antes de responder.

Modo Casual vs Formal

Casual Formal
Sem /nid:init Com .claude/nid-project.json
Skills/agentes disponíveis Ciclo SDD completo
Gates opcionais Gates obrigatórios + hooks
Tarefas pontuais Projetos rastreáveis

Verification Before Completion (VBC)

Princípio #3 da Constituição: não declarar "pronto" sem evidência da forma certa para a mídia. BI = baseline comparison; ETL = DQ asserts; AI = eval golden. Ver nid-verification-gates.

Modo Didático

Princípio #1 da Constituição: todo agente explica [O QUE] + [POR QUE] + [COMO] em toda resposta relevante. Ver 1.6 Modo Didático.

ADR (Architecture Decision Record)

Documento em docs/adr/YYYYMMDD-N-<topico>.md que registra decisão arquitetural com contexto, opções consideradas e justificativa. Obrigatório para override da Constituição.

Bucket

Agrupamento de skills por domínio: bi/, data/, ai-engineering/, azure-data/, azure-ai/, methodology/, m365-power-platform/, etc.

Plan 3b, 3c...

Nomenclatura interna das sessões de criação do kit. "Plan 3b azure-data/" = sessão que criou as 5 skills de azure-data/. Visible nos handoffs em docs/tasks/.

1.1 Instalação do nid-spec-kit

Como instalar o nid-spec-kit globalmente no Claude Code (Windows + Linux/Mac)

Resumo

O nid-spec-kit é instalado uma única vez globalmente. Após a instalação, skills e agentes ficam disponíveis em qualquer projeto Claude Code sem configuração adicional.

Pré-requisitos

  • Claude Code instalado (CLI claude disponível no terminal)
  • Git instalado
  • Python 3.10+ (para ferramentas do kit como o build do UniversiNID)
  • Acesso ao repositório nid-spec-kit (GitHub DELP ou clone local)

Instalação — Windows (PowerShell)

# 1. Clone o repositório
git clone https://github.com/delp-nid/nid-spec-kit.git C:\dev\nid-spec-kit

# 2. Rode o script de instalação
cd C:\dev\nid-spec-kit
.\install.ps1

# 3. Verifique a instalação
claude --version

O install.ps1 registra o plugin em %APPDATA%\Claude\claude_desktop_config.json e copia hooks.

Instalação — Linux / Mac (bash)

# 1. Clone o repositório
git clone https://github.com/delp-nid/nid-spec-kit.git ~/nid-spec-kit

# 2. Rode o script de instalação
cd ~/nid-spec-kit && chmod +x install.sh && ./install.sh

O que o instalador faz

Etapa Ação
1 Registra nid-spec-kit em ~/.claude/plugins.json
2 Copia hooks para ~/.claude/hooks/ (pre/post tool-use, session-start)
3 Verifica dependências: superpowers plugin + Python
4 Exibe confirmação com versão instalada

Verificar instalação

Abra qualquer pasta no Claude Code e teste:

# Em qualquer chat Claude Code:
"use a skill nid-dax-medidas"

Se a skill responder com contexto DAX DELP, a instalação funcionou.

Atualizar o kit

cd C:\dev\nid-spec-kit
git pull
.\install.ps1  # re-executa instalação com nova versão

Nota: O install.ps1 atual está em versão beta — pode precisar de ajustes manuais dependendo da configuração Claude Code da sua máquina. Em caso de problema, reporte no canal NID.

Resolução de problemas

Problema Causa provável Solução
Skill não encontrada Plugin não registrado Verificar ~/.claude/plugins.json
Hook não dispara Permissão negada Rodar Claude Code como admin (Windows)
Python não encontrado PATH incompleto Adicionar Python ao PATH do sistema

1.2 Casual vs Formal — dois modos de uso

Quando usar cada modo e como transitar entre eles

Resumo

O NID tem dois modos de operação: Casual (skills e agentes à la carte, sem burocracia) e Formal (ciclo SDD completo com gates e hooks). A maioria das tarefas do dia a dia é Casual. Formal é para projetos que precisam de rastreabilidade.

Detecção automática

O hook session-start/load-nid-context detecta o modo automaticamente:

📁 pasta sem .claude/nid-project.json  →  MODO CASUAL
📁 pasta com  .claude/nid-project.json  →  MODO FORMAL

Não há nada para configurar manualmente — o kit detecta ao abrir o Claude Code na pasta.

Comparativo

Aspecto Casual Formal
Skills/agentes disponíveis ✅ Todas ✅ Todas
Modo Didático ✅ ✅
/nid:specify antes de plano ❌ Opcional ✅ Obrigatório
/nid:gate antes de implementar ❌ Sugerido ✅ Bloqueante
Evidência formal de verificação Sugerida Obrigatória
ADR para decisões ❌ ✅ Obrigatório
Hooks ativos ❌ ✅
.claude/nid-project.json ❌ Não existe ✅ Criado por /nid:init

Modo Casual — quando usar

  • Criar uma medida DAX pontual
  • Debugar pipeline ETL
  • Gerar documentação de feature
  • Consultar skill sem projeto aberto
  • Experimentar nova ferramenta
# Exemplo casual:
"use a skill nid-dax-medidas e cria uma medida de Faturamento MTD"

Modo Formal — quando usar

  • Projeto novo de médio ou grande porte
  • Precisa de rastreabilidade (cliente, audit, time)
  • Múltiplos devs trabalhando em paralelo
  • Projeto com gates de qualidade obrigatórios
# Ativar modo formal em pasta de projeto:
/nid:init bi         # projeto BI
/nid:init etl        # projeto ETL
/nid:init azure-ai   # projeto Azure AI

Transitar de Casual para Formal

Em qualquer ponto de um chat casual:

/nid:init <tipo>

Isso cria .claude/nid-project.json, ativa hooks e gradua para modo Formal. O histórico da sessão é preservado.

Transitar de Formal para Casual

Basta abrir Claude Code em outra pasta sem nid-project.json. Não há "desativação" — é baseado em presença de arquivo.

Dica prática: Comece sempre em Casual para tarefas pontuais. Se o escopo crescer e precisar de rastreabilidade, rode /nid:init e continue.

1.3 Primeira skill — usando nid-dax-medidas

Passo a passo para usar sua primeira skill NID em um exemplo real

Resumo

Skills são ativadas por instrução direta no chat. Não há comando mágico — você simplesmente diz ao Claude para usar a skill. Vamos usar nid-dax-medidas como exemplo, mas o padrão vale para qualquer skill do kit.

Anatomia de uma skill

Toda skill NID tem a estrutura:

skills/bi/nid-dax-medidas/
├── SKILL.md          ← regras, quando usar, anti-patterns
└── references/
    ├── naming-convention.md
    ├── time-intelligence.md
    └── performance-tips.md

SKILL.md é carregado automaticamente quando você invoca a skill. Os arquivos em references/ são carregados sob demanda — só quando necessário. Isso mantém o contexto enxuto.

Passo 1 — Invocar a skill

"Use a skill nid-dax-medidas. Preciso de uma medida de Faturamento do Mês (MTD)."

O agente carrega SKILL.md, lê as regras NID de naming e time intelligence, e responde com a medida já no padrão correto.

O que você recebe

O agente responde no Modo Didático (Princípio #1):

[O QUE] Criando medida DAX de Faturamento MTD seguindo padrão NID.

[POR QUE] MTD (Month-to-Date) agrega do dia 1 do mês até hoje — útil
para acompanhamento diário vs meta mensal.

[COMO] Usando DATESMTD() com a data table DELP (período 21 a 20).

[Código]
Faturamento MTD :=
CALCULATE(
    [Faturamento Total],
    DATESMTD('dim_calendario'[date])
)

[Próximo passo] Quer adicionar comparação MTD vs mesmo período ano anterior?

Passo 2 — Pedir referência aprofundada

Se precisar de mais contexto:

"Carregue as referências de time intelligence da skill nid-dax-medidas."

O agente lê references/time-intelligence.md e expande com exemplos, edge cases e anti-patterns.

Combinando skills

Você pode usar múltiplas skills na mesma sessão:

"Use nid-power-bi-modelagem para revisar o modelo e depois
nid-dax-medidas para adicionar as medidas de Faturamento MTD e YTD."

Anti-patterns comuns

  • ❌ Pedir medida sem especificar o contexto (qual tabela fato, qual dim_data)
  • ❌ Nomear medida sem seguir convenção NID (fat MTD em vez de Faturamento MTD)
  • ❌ Esquecer de testar a medida no modelo — sempre verificar no Power BI Desktop

1.4 Primeiro agente — nid-bi-engineer

Como invocar e trabalhar com agentes especializados NID

Resumo

Agentes são personas especializadas. Diferente de skills (que são instruções), agentes têm papel próprio, voz e responsabilidades. Você "contrata" o agente para uma tarefa, e ele usa as skills relevantes por conta própria.

Diferença entre skill e agente

Skill Agente
É Conjunto de regras/padrões Persona especializada
Faz Instrui como fazer X Age como especialista em X

1.5 Os 10 Princípios da Constituição NID

Os 10 princípios universais que todo agente NID segue — e você precisa conhecer

Resumo

A CONSTITUTION.md define 10 princípios que todo agente NID segue sem exceção. Conhecê-los ajuda você a entender o comportamento dos agentes, a pedir melhor, e a identificar quando um agente saiu do padrão.

Os 10 Princípios

1. Modo Didático sempre

Todo agente, em toda resposta, explica:

[O QUE]    — ação concreta sendo realizada
[POR QUE]  — qual problema resolve
[COMO]     — conceito técnico por trás
[Próximo]  — transição clara (opcional)

Por que isso importa: combate o "caixa preta" — você aprende enquanto recebe o resultado.

2. pt-BR para comunicação humana

Output ao usuário em português brasileiro. Código e identifiers ficam em inglês quando a stack pede. Comentários, mensagens de erro, documentação: sempre pt-BR.

3. Verification Before Completion (VBC)

Não declarar "pronto" sem evidência adequada para a mídia:

Mídia Forma de evidência
BI/DAX Medida vs baseline em sample dataset
ETL DQ asserts antes/depois
AI Eval ≥5 exemplos golden + métrica
M365 Scripted conversation ≥3 caminhos
Web/MES TDD (vitest + playwright)

4. Source-of-truth referenced

Toda afirmação técnica cita fonte: doc Microsoft Learn, ADR, knowledge/, código existente. Nunca afirmar sem citar. Em incerteza: declarar [PENDENTE].

5. Não inventar dados do mundo real

Se não está no input, em knowledge/, ou em fonte citada → é [PENDENTE] + SIT (Solicitação de Informação Técnica). Aplica-se a: regras de negócio DELP, schemas de tabelas, parâmetros de modelo.

6. Aprovação humana em gates explícitos

Agente nunca avança fase sem confirmação humana. Gates obrigatórios:
- /nid:specify → entre brainstorm e spec final
- /nid:gate → entre plano e implementação (bloqueante)
- Antes de qualquer destruição ou envio externo

7. Red-team antes de implement

/nid:gate é obrigatório entre /nid:plan e /nid:implement em projetos formais. O nid-red-team ataca adversarialmente. Hook pre-tool-use/block-implement-without-gate enforça automaticamente.

8. Conhecimento volátil mora em knowledge/

Portfólio NID, tenant M365, ferramentas homologadas, lições aprendidas → versionados em knowledge/, nunca presos no prompt. O NID acumula conhecimento, não esquece.

9. Commits semânticos

Para projetos com git: feat:, fix:, chore:, refactor:, test:, docs:, style:, perf:, ci:. Mensagem em pt-BR após o tipo.

feat: adiciona medida DAX MTD para faturamento por unidade
fix: corrige filtro de período na medida YTD
docs: atualiza SKILL.md com anti-pattern de FILTER()

10. Trust user direction

Hierarquia de autoridade em conflito:
1. Instrução explícita do usuário (override máximo)
2. CLAUDE.md do projeto
3. CONSTITUTION.md do projeto
4. CONSTITUTION.md mestre
5. Defaults do kit

O kit é servo, não policial. Você pode fazer override de qualquer regra — só registre em ADR.

Como usar os princípios

  • Você: se um agente não está em Modo Didático, peça: "Explique o raciocínio por trás desta escolha"
  • Você: se quiser fazer override de um princípio, diga explicitamente: "Para esta sessão, pule a verificação formal"
  • Você: se suspeitar que o agente inventou dado DELP, questione: "Qual é a fonte desta informação?"

1.6 Modo Didático — aprender enquanto entrega

Como o Modo Didático funciona na prática, com exemplos reais de antes e depois

Resumo

Modo Didático é o Princípio #1 da Constituição: todo agente NID explica o quê está fazendo, por que, e como em toda resposta relevante. Não é verbosidade — é aprendizado embutido na entrega.

O padrão [O QUE] / [POR QUE] / [COMO]

[O QUE]    Ação concreta sendo realizada
[POR QUE]  Qual problema resolve ou motivação da escolha
[COMO]     Conceito técnico por trás (ensinar enquanto entrega)
[Próximo]  (opcional) Transição clara para o próximo passo

Exemplo: SEM Modo Didático

Crie uma medida de Faturamento MTD.
---
Faturamento MTD :=
CALCULATE([Faturamento Total], DATESMTD('dim_calendario'[date]))

Funciona, mas você não sabe por que DATESMTD foi escolhido, se há alternativas, ou o que pode dar errado.

Exemplo: COM Modo Didático

[O QUE] Criando medida de Faturamento MTD (Month-to-Date).

[POR QUE] MTD acumula do dia 1 do mês até hoje — permite acompanhamento
diário vs meta mensal sem precisar de segmentação manual.

[COMO] DATESMTD() é a função de time intelligence mais simples para MTD.
Ela usa a coluna de data da dim_calendario (que precisa ser contínua e
sem lacunas) para criar o contexto de filtro acumulado. Alternativa
seria TOTALYTD()+filtro de mês — mais complexo sem vantagem real aqui.

Faturamento MTD :=
CALCULATE(
    [Faturamento Total],
    DATESMTD('dim_calendario'[date])
)

[Próximo] Quer criar YTD (Year-to-Date) e vs LY (Last Year) para
completar o painel de acompanhamento?

Por que isso importa

  • Você aprende enquanto entrega: a próxima vez que precisar de MTD, você sabe o raciocínio
  • Detecção de erro fácil: se o "POR QUE" estiver errado, você percebe antes de usar
  • Comunicação com stakeholders: você pode repassar o raciocínio para o time
  • Cultura de conhecimento: o NID acumula expertise, não só output

Como ativar e controlar

O Modo Didático está sempre ativo por padrão. Para controlar:

# Mais detalhado (quando aprendendo algo novo):
"Explique em detalhes o raciocínio por trás desta escolha."

# Mais direto (quando já entende):
"Modo Didático resumido — só o código e o risco principal."

# Desativar pontualmente:
"Para esta tarefa, entrega direto sem explicação."

Importante: Você pode pedir para reduzir o Modo Didático (Princípio #10 — Trust user direction). Mas nunca remova a parte de riscos/anti-patterns — isso protege a entrega.

Modo Didático em code review

[O QUE] Revisando medida Faturamento Bruto.

[POR QUE] FILTER(ALL(...)) foi usado onde REMOVEFILTERS() bastaria.

[COMO] ALL() retorna tabela, FILTER(ALL()) itera linha a linha.
REMOVEFILTERS() é mais eficiente para limpar contexto sem
iteração. Em 50M linhas: REMOVEFILTERS = instantâneo,
FILTER(ALL) = segundos.

→ Substituição sugerida: [código]

2.1 Ciclo SDD — do brief ao código

O ciclo SDD completo passo a passo: do brief inicial ao código revisado

Resumo

O SDD (Spec-Driven Development) no NID é um ciclo de 5 fases com aprovação humana em cada transição. Este módulo detalha cada fase, o que acontece dentro dela, e quando você pode (ou deve) pular etapas.

Diagrama do ciclo

 ┌─────────────┐     aprovação    ┌─────────────┐     aprovação
 │ /nid:specify │ ──────────────► │  /nid:plan  │ ──────────────►
 │  Brainstorm  │                 │  Plano      │
 │  → Spec      │                 │  técnico    │
 └─────────────┘                 └─────────────┘
                                                         │
                                                  aprovação implícita
                                                         │
 ┌─────────────┐  GO decidido    ┌─────────────┐         ▼
 │/nid:implement│ ◄────────────── │  /nid:gate  │ ◄── /nid:tasks
 │  Execução   │                 │  Red-team   │
 │  + verify   │                 │  GO/NO-GO   │
 └─────────────┘                 └─────────────┘

Fase 1 — Especificação (/nid:specify)

Quem: você + nid-product-manager

O que acontece:
1. Você descreve o problema em linguagem natural
2. nid-product-manager faz perguntas de clarificação (requisitos, restrições, stakeholders)
3. Brainstorm de abordagens (≥2 opções com trade-offs)
4. Você aprova uma abordagem → spec finalizada em docs/spec/YYYYMMDD-<topico>.md

Aprovação necessária: você explicitamente diz "spec aprovada" para avançar

Quando pular: tarefas pontuais (Casual). Nunca pular em projetos com >1 dev ou >1 semana.

Fase 2 — Planejamento (/nid:plan)

Quem: nid-architect + agente vertical do domínio

O que acontece:
1. Lê a spec aprovada
2. Detalha cada componente (stack, arquitetura, dependências)
3. Estima esforço por tarefa
4. Produz docs/plans/YYYYMMDD-<topico>.md com lista de tasks

Aprovação necessária: você revisa e aprova o plano técnico

Output típico:

## Plan — ETL Faturamento Diário
Fase: implementação via /nid:tasks

Tasks:
1. [ ] dim_produto: upsert via pyarrow + Kimball
2. [ ] fato_vendas: incremental via Tumbling Window
3. [ ] DQ asserts: 5 mínimos antes do promote
4. [ ] test: DQ asserts + row counts baseline

Fase 3 — Tasks (/nid:tasks)

Quem: nid-tech-lead

O que acontece:
1. Plano → lista de tasks com: agente responsável, evidência de verificação, dependências
2. Estimativa de paralelismo (quais rodam em paralelo vs sequencial)

Aprovação necessária: implícita (tasks são insumo do gate)

Fase 4 — Gate (/nid:gate) ⚠️ BLOQUEANTE

Quem: nid-red-team

Este é o único gate que bloqueia automaticamente via hook. Ver 2.2 /nid:gate explicado.

Fase 5 — Implementação (/nid:implement)

Quem: agentes verticais (BI, Data, Azure, etc.) coordenados por nid-tech-lead

O que acontece:
1. Tasks executadas uma a uma (ou em paralelo se disponível)
2. Cada task tem verificação declarada — não marca como done sem evidência
3. nid-tech-lead consolida e reporta progresso

Loop de progresso:

task → execute → verify → mark done → next task
                    ↓
              se falhar: investigar antes de tentar de novo

Tabela de decisão — quando usar cada fase?

Situação Specify? Plan? Gate? Implement?
Medida DAX pontual ❌ ❌ ❌ direta
Feature nova em ApontDELP ✅ ✅ ✅ via implement
Pipeline ETL de média complexidade ✅ ✅ sugerido via implement
Correção de bug (<1h) ❌ ❌ ❌ direta
Projeto >1 dev ✅ ✅ ✅ via implement
Integração com sistema externo ✅ ✅ ✅ via implement

2.2 /nid:gate — o checkpoint bloqueante

Como funciona o /nid:gate, o que o nid-red-team verifica, e como tomar a decisão GO/NO-GO

Resumo

O /nid:gate é o único ponto no ciclo SDD que é obrigatório e bloqueante em projetos Formais. O nid-red-team assume o papel de crítico adversarial — tenta encontrar tudo que pode dar errado no plano antes de qualquer código ser escrito.

Por que o gate existe

Custo de corrigir um bug:
- Na spec: 1x
- No plano: 5x
- No código: 20x
- Em produção: 100x

O gate é o "revisor do plano" antes de qualquer investimento de implementação. É mais barato encontrar buracos agora do que refatorar depois.

O que o nid-red-team verifica

O agente ataca o plano em 6 dimensões:

1. Completude de requisitos

  • Os requisitos estão todos cobertos?
  • Algum edge case foi ignorado?
  • Há requisitos implícitos que não foram declarados?

2. Viabilidade técnica

  • A stack proposta resolve o problema?
  • Existe uma solução mais simples?
  • As estimativas são realistas?

3. Segurança e compliance

  • Há secrets hardcoded ou em risco?
  • LGPD/GDPR se dados pessoais estiverem envolvidos?
  • Permissões mínimas (Managed Identity aplicado)?

4. Pontos de falha

  • O que acontece se passo X falhar?
  • Há idempotência onde necessário?
  • Dead-letter queue para mensageria?

5. Verificabilidade

  • Cada task tem critério de sucesso claro?
  • A evidência de verificação é objetiva (não subjetiva)?
  • Como detectar regressão no futuro?

6. Dependências e riscos externos

  • Há dependência de sistemas externos sem fallback?
  • O timing de deploy cria janela de inconsistência?

Formato do relatório de gate

## Gate Report — ETL Faturamento Diário — 2026-05-07

### Riscos críticos (bloqueiam GO)
1. FALTA dead-letter para fila de eventos — falha silenciosa em prod
2. Credencial de banco em config.py — violação Princípio #5 (zero secret em código)

### Riscos moderados (alertas para implementação)
3. Self-hosted IR com 1 nó — sem HA; falha = pipeline parado
4. Sem asserção de row count no promote curated→DWH

### Itens OK
5. Managed Identity configurado para Storage Account
6. Tumbling Window com retry e timeout declarados

---
Decisão: NO-GO — corrigir riscos críticos 1 e 2 antes de implementar.
Retomar gate após correção.

Tomando a decisão GO/NO-GO

Situação Decisão sugerida
Sem riscos críticos GO — pode ter alertas moderados, implementação pode começar
1 risco crítico simples NO-GO leve — corrigir (5 min) + re-gate rápido
Múltiplos riscos críticos NO-GO — voltar ao plano
Risco crítico de segurança NO-GO IMEDIATO — escalar para Henrique

Você decide. O nid-red-team recomenda, mas a decisão GO/NO-GO é sempre humana (Princípio #6).

Override do gate (com justificativa)

Em casos excepcionais (protótipo descartável, demo interna):

"Para esta sessão, declaro GO sem gate completo porque:
[justificativa]. Registrando em ADR docs/adr/2026-05-07-1-gate-override.md."

O hook aceita o override mas exige justificativa registrada. Nunca silencioso.

2.3 Verificação por mídia — VBC na prática

Como aplicar Verification Before Completion em cada tipo de projeto NID

Resumo

VBC (Verification Before Completion — Princípio #3) significa que "rodei e funcionou" nunca é evidência suficiente. Cada mídia tem sua forma de evidência objetiva. Este guia mostra como aplicar VBC em cada domínio NID.

A regra geral

Antes de declarar "pronto":
1. Identifique a mídia do artefato
2. Aplique a forma de evidência correspondente
3. Documente a evidência (screenshot, log, assert output, etc.)
4. Só então commite/entregue

Evidência por domínio

BI / DAX

Forma: comparação medida nova vs baseline em sample dataset

# Exemplo de baseline comparison manual:
# Medida antiga → exportar para Excel → medida nova → comparar valores
# Tolerância: 0 diferença para valores históricos
# Aceito: diferença justificável em período corrente (dados frescos)

Checklist mínimo:
- [ ] Medida calcula valor correto em ≥3 períodos (MTD, YTD, MêsEspecífico)
- [ ] Sem erros de contexto filtro em slicers de unidade/produto
- [ ] Formatação numérica correta (separador decimal, símbolo)
- [ ] Nome segue convenção NID (Faturamento MTD não fat_mtd nem FatMTD)

ETL / Data

Forma: asserções de DQ antes/depois da carga

# Exemplo com nid-data-quality-asserts:
def test_fato_vendas_carga():
    assert row_count("fato_vendas") > baseline_count  # sem deleção
    assert null_count("fato_vendas", "id_produto") == 0  # FK integridade
    assert max_date("fato_vendas", "data") >= yesterday()  # frescor
    assert row_count("fato_vendas") == row_count("staging_vendas_validado")  # completude
    assert duplicate_count("fato_vendas", ["id_venda"]) == 0  # unicidade

Mínimo: 5 asserções, todas devem passar. Falha = pipeline falha (sem manual bypass).

AI Engineering / Azure AI

Forma: eval suite ≥5 exemplos golden + métrica quantitativa + smoke endpoint

# Exemplo nid-eval-suite:
# golden_examples = [
#   {"input": "qual faturamento Jan?", "expected_contains": "Janeiro"},
#   {"input": "top 5 produtos", "expected_has_list": True},
#   ...
# ]
# Métrica: precision@5 ≥ 0.8, latência < 3s

Mínimo: 5 goldens, métrica declarada e atingida, smoke test em endpoint real (não mock).

M365 / Power Platform / Copilot Studio

Forma: scripted conversation ≥3 caminhos (feliz, edge, erro) + teste de conectores

Caminho feliz: "Quero aprovar uma solicitação de férias" → fluxo completo
Edge case: aprovador ausente → redirecionamento correto
Erro: SharePoint offline → mensagem de fallback amigável

Conectores: cada conector listado no fluxo deve ter smoke test real (não simulado).

Azure Data (Functions, ADF, Logic Apps, Events)

Forma: DQ asserts + idempotência testada

# Idempotência: rodar 2x produz mesmo estado
invoke_pipeline() && sleep 30 && invoke_pipeline()
assert_state_identical()  # row counts, checksums, etc.

# Smoke: trigger manual + verificar AppInsights/Monitor sem erros

Web / MES (ApontDELP)

Forma: TDD clássico — vitest (unit) + playwright (e2e)

// Exemplo mínimo:
describe("apontamento", () => {
  it("cria apontamento com dados válidos", async () => {
    // ...
  });
  it("rejeita apontamento sem colaborador", async () => {
    // ...
  });
});
// playwright: golden path do fluxo completo

Slides / Comunicação

Forma: checklist visual + revisão por par humano

[ ] Slide não excede 6 bullets por slide
[ ] Fontes Barlow/Open Sans aplicadas
[ ] Paleta DELP (vermelho #cc0f10, laranja #dd8f1a)
[ ] Revisado por ≥1 pessoa do time antes de envio
[ ] Números verificados contra fonte primária

API / Postman

Forma: Newman collection com asserções de schema e status

newman run collection.json --env prod.json
# Esperado: 0 falhas, todos os assertions passam

Anti-patterns de verificação

Anti-pattern Por quê é inválido
"Testei manualmente e funcionou" Não reproduzível, sem baseline
"O QA vai testar depois" VBC é do desenvolvedor, não só do QA
"Só muda a lógica, não precisa testar" Regressão silenciosa é o risco mais comum
"O pipeline rodou sem erro" Sem erro ≠ resultado correto

2.5 Knowledge base — como usar e manter

Como a knowledge base funciona, o que vai nela, e como mantê-la atualizada

Resumo

A knowledge/ é a memória persistente do NID entre sessões. Tudo que os agentes precisam saber sobre o contexto DELP (ferramentas, regras de negócio, decisões, lições) fica aqui. Sem ela, cada sessão começa do zero.

Por que existe

LLMs não têm memória entre sessões. O agente que criou o ETL de faturamento ontem não "lembra" nada hoje. A knowledge/ resolve isso: é lida pelos agentes no início de cada sessão como contexto persistente.

Princípio #8: "Conhecimento volátil mora em knowledge/. O NID acumula conhecimento, não esquece."

Estrutura atual

knowledge/
├── portfólio/          # projetos ativos e seus stacks
├── ferramentas/        # ferramentas homologadas e versões
├── governança/         # regras DELP (calendário, naming, etc.)
├── glossário/          # termos específicos DELP
├── lições/             # lições aprendidas de incidentes/projetos
└── prompts/            # banco de prompts #001-499 (link para prompts/)

Status atual (2026-05-07): knowledge/ tem estrutura mas ainda sem conteúdo populado — pendente em sessões futuras do kit.

O que vai na knowledge base

Tipo Exemplo Onde
Stack homologada "Azure Functions: Python v2, Premium EP1 prod" ferramentas/azure.md
Regra de negócio "Período DELP = dia 21 ao 20 do mês seguinte" governança/calendario.md
Decisão técnica "Não usar Terraform — decisão: Bicep (ver ADR 2026-04-28-1)" governança/iac.md
Lição aprendida "SSPI falha em conexão Azure → usar Managed Identity" lições/azure-auth.md
Portfólio ativo "ApontDELP: Next.js + TypeScript + Prisma + PostgreSQL" portfólio/apontdelp.md

O que NÃO vai na knowledge base

  • Código-fonte → fica no repo do projeto
  • Dados reais de produção → nunca em repositório
  • Outputs temporários → são efêmeros, não knowledge
  • Conteúdo que já está em SKILL.md → não duplicar

Como usar durante uma sessão

O agente lê knowledge/ automaticamente quando disponível. Para reforçar:

"Antes de responder, consulte knowledge/governança/calendario.md para o
período DELP correto."

Ou para contexto específico:

"Use knowledge/portfólio/apontdelp.md como contexto da stack atual."

Como atualizar

Quando atualizar

  • Nova ferramenta homologada pelo NID
  • Decisão técnica tomada (stack, padrão, convenção)
  • Lição aprendida de incidente ou projeto
  • Mudança em regra de negócio DELP

Processo de atualização

# 1. Identificar o arquivo certo em knowledge/
# 2. Editar com o conteúdo novo
# 3. Commitar com mensagem descritiva

git add knowledge/ferramentas/azure.md
git commit -m "docs(knowledge): adiciona Python v2 como padrão Azure Functions

Decisão tomada em Plan 3b azure-data. Validada com nid-azure-data-engineer.
Referência: ADR 2026-04-28-12-azure-functions-python-v2.md"

Cadência sugerida

  • Após cada projeto que gere lição nova
  • Mensalmente para revisão de ferramentas homologadas
  • Imediatamente para mudanças em regras de negócio

Sincronia com skills

Quando uma skill SKILL.md menciona algo que é específico do DELP (ex: "período 21 a 20"), o fato real mora em knowledge/governança/, e a skill apenas referencia. Isso evita que a mesma regra apareça em 10 lugares com risco de divergência.

3.1 /nid:skill-create — criando novas skills

3.2 /nid:rules-distill — extraindo padrões de exemplos

Como usar /nid:rules-distill para transformar exemplos aprovados em skill ou princípio

Resumo

/nid:rules-distill lê N exemplos de trabalho aprovado e propõe uma skill nova ou princípio novo. É o mecanismo de "aprendizado organizacional automatizado" — o que você fez bem vira regra do kit.

A lógica por trás

3+ exemplos aprovados de X
    → /nid:rules-distill <pasta>
    → nid-rules-distill-agent analisa padrões
    → proposta: skill nova OU princípio OU adição a skill existente
    → você aprova ou refina
    → codificado no kit

É o ciclo inverso da skill: em vez de escrever regras manualmente, você acumula exemplos e distila as regras.

Quando usar

  • Você fez X de forma similar ≥3 vezes e quer codificar o padrão
  • Houve debate sobre "a forma certa de fazer Y" — resolver com exemplos, não opiniões
  • Você quer verificar se as regras da skill atual ainda refletem a prática real

Não usar:
- Com apenas 1-2 exemplos (pouco para identificar padrão)
- Quando o processo ainda está mudando (espere estabilizar)

Exemplo de uso

# Você tem 4 relatórios Power BI aprovados em:
ls docs/exemplos/narrativas-executivas/

# Rodar distilação:
/nid:rules-distill docs/exemplos/narrativas-executivas/

# O agente analisa os 4 e propõe:
# "Padrão identificado em todos os 4 exemplos:
#  1. Sempre abre com o KPI mais crítico (variação YTD)
#  2. Usa 3 seções: Destaques / Riscos / Próximos Passos
#  3. Números sempre com comparativo (vs meta ou vs LY)
#  4. Máximo 5 bullets por seção
#
# Proposta: adicionar à skill nid-power-bi-narrativa-executiva
# seção 'Estrutura padrão de narrativa DELP' com estas 4 regras."

O que você aprova

O agente não commita nada sozinho. Ele propõe, você decide:

Opção Quando escolher
"Aprovado, criar nova skill nid-X" Padrão suficientemente independente
"Aprovado, adicionar à skill nid-Y" Padrão complementa skill existente
"Aprovado como princípio em CONSTITUTION.md" Regra universal, aplica a todos os domínios
"Refinar proposta: [feedback]" Proposta está quase certa mas precisa ajuste
"Não aprovo — [razão]" Padrão não é real ou é circunstancial

Estrutura de exemplos para boa distilação

Exemplos ruins → distilação ruim. Para resultados bons:

docs/exemplos/<topico>/
├── exemplo-01-[descricao].md  # aprovado e usado em prod
├── exemplo-02-[descricao].md  # aprovado e usado em prod
├── exemplo-03-[descricao].md  # aprovado e usado em prod
└── meta.md                    # contexto: por que estes são bons?

O meta.md é opcional mas ajuda o agente a entender o critério de aprovação usado.

Saída típica da distilação

## Análise de /nid:rules-distill — narrativas-executivas/

### Padrões identificados (presentes em ≥3/4 exemplos)
1. Abre com KPI de variação YTD em negrito
2. Seções: Destaques / Riscos / Próximos Passos
3. Máximo 5 bullets por seção (todos os 4 seguem isso)
4. Número sempre tem comparativo (vs meta ou vs LY)

### Padrões presentes em apenas 1 exemplo (não distilados)
5. Gráfico Mermaid de tendência (só no exemplo-04)

### Proposta
Adicionar à `nid-power-bi-narrativa-executiva` SKILL.md seção:
"## Estrutura padrão de narrativa DELP" com as regras 1-4.

Aprovação necessária antes de commitar.

3.3 /nid:eval — avaliando skills e agentes

Como usar /nid:eval para verificar que skills e agentes continuam no padrão

Resumo

Skills e agentes podem "driftar" — o modelo muda, o contexto muda, ou a skill foi editada e o comportamento esperado ficou diferente. /nid:eval roda uma suite de testes para detectar esse drift antes que chegue à produção.

O que é drift

Skill nid-dax-medidas em Março:
→ "Faturamento MTD" → código correto, naming certo

Skill nid-dax-medidas em Junho (após edição para añadir rule):
→ "Faturamento MTD" → código correto, mas naming virou "fat_MTD"

Isso é drift — a skill mudou de comportamento sem intenção. Eval detecta.

Estrutura de um eval

Toda skill que tem verification: eval em SKILL.md deve ter:

skills/<bucket>/nid-<nome>/
├── SKILL.md
├── references/
└── examples/
    ├── golden-01.md      # exemplo canônico aprovado
    ├── golden-02.md
    ├── golden-03.md
    └── eval-config.yaml  # configuração da suite

eval-config.yaml mínimo:

skill: nid-dax-medidas
golden_examples:
  - golden-01.md
  - golden-02.md
  - golden-03.md
checks:
  - type: contains
    field: output
    value: "DATESMTD"      # função correta deve aparecer
  - type: not_contains
    field: output
    value: "TOTALYTD"      # anti-pattern para MTD
  - type: naming_convention
    pattern: "^[A-Z][a-z]+ [A-Z]{2,4}$"  # "Faturamento MTD"
metrics:
  min_pass_rate: 0.8       # 80% dos goldens devem passar

Como rodar o eval

# Eval de uma skill específica:
/nid:eval nid-dax-medidas

# Eval de um agente:
/nid:eval nid-bi-engineer

# Saída esperada:
# golden-01: PASS (3/3 checks)
# golden-02: PASS (3/3 checks)
# golden-03: FAIL — naming: output "faturamento_MTD" não segue convenção
# Pass rate: 2/3 = 67% < 80% mínimo
# DRIFT DETECTADO em nid-dax-medidas. Ver golden-03 para contexto.

Quando rodar eval

Momento Por quê
Após editar qualquer SKILL.md Verificar que mudança não quebrou comportamento
Após atualização de modelo Claude Comportamento pode mudar com novo modelo
Antes de deploy em prod Gate de qualidade automatizado
Mensalmente em skills críticas Detecção proativa de drift gradual

Golden examples — como escrever

Um golden example é um par (input, expected output) aprovado por um humano. Deve ser:

  • Real: veio de uma tarefa real aprovada, não inventado
  • Específico: não genérico demais (eval fraco) nem específico demais (frágil)
  • Representativo: cobre o caso de uso principal da skill
# Golden example 01 — Medida MTD básica

## Input
"Use nid-dax-medidas. Crie medida de Faturamento MTD para modelo
com fato_vendas (coluna valor_liquido) e dim_calendario."

## Expected output (padrões)
- Deve conter: DATESMTD
- Deve conter: CALCULATE
- Nome deve ser: "Faturamento MTD"
- Deve usar: dim_calendario[date]
- Não deve usar: TOTALYTD

## Aprovado por: Henrique Emiliano — 2026-04-15

3.6 Override de constituição — quando e como usar ADR

Como fazer override de um princípio da Constituição NID e registrar em ADR

Resumo

A Constituição NID define 10 princípios não-negociáveis — mas o Princípio #10 diz que o usuário sempre tem autoridade máxima. Quando um projeto precisa de exceção a um princípio, o mecanismo é o ADR (Architecture Decision Record).

O que é um ADR

Um ADR é um documento que registra:
- Contexto: por que a situação padrão não se aplica
- Decisão: qual override foi feito
- Consequências: o que muda, quais riscos aceitos

Não é burocracia — é memória organizacional. Sem ADR, o "por que fizemos assim" some quando o dev sai.

Quando fazer override

Princípio Exemplo de override legítimo
VBC (Princípio #3) Protótipo descartável — gate de qualidade adiado
Gate obrigatório (Princípio #7) Deploy de hotfix crítico em prod — sem tempo para gate formal
pt-BR (Princípio #2) Skill bilíngue para onboarding de dev internacional
Commits semânticos (Princípio #9) Squash de branch experimental para limpar histórico
Source-of-truth (Princípio #4) Estimativa rápida sem fonte citada (documentado como estimativa)

Não fazer override de:
- Managed Identity + zero secrets em código (segurança)

import anthropic

client = anthropic.Anthropic()
MAX_ITERATIONS = 10
COST_CAP_USD = 2.0

def run_agent(user_query: str) -> str:
    messages = [{"role": "user", "content": user_query}]
    tools = [search_documents_tool, get_document_tool]
    iterations = 0
    total_tokens = 0

    while iterations < MAX_ITERATIONS:
        response = client.messages.create(
            model="claude-opus-4-7",
            max_tokens=4096,
            system=SYSTEM_PROMPT,
            tools=tools,
            messages=messages,
        )
        total_tokens += response.usage.input_tokens + response.usage.output_tokens

        # Stop criterion 1: resposta final
        if response.stop_reason == "end_turn":
            log_audit(iterations, total_tokens, "end_turn")
            return extract_text(response)

        # Stop criterion 2: cost cap
        if total_tokens * 0.000015 > COST_CAP_USD:
            log_audit(iterations, total_tokens, "cost_cap")
            return "Limite de custo atingido. Tente uma pergunta mais específica."

        # Stop criterion 3: eval-gate (qualidade do resultado)
        if should_stop_on_quality(response):
            return handle_quality_gate(response)

        messages = process_tool_calls(response, messages)
        iterations += 1

  ativo     Boolean       @default(true)

  ativo: z.boolean().default(true),

Estimativa Por fase, em dias "algumas semanas"

Verificação obrigatória

  • [ ] Contexto quantificado (tempo perdido, erro, custo)
  • [ ] Objetivo em 1 frase que um não-técnico entende
  • [ ] Escopo OUT explícito (evita scope creep)
  • [ ] Critérios de sucesso mensuráveis com prazo
  • [ ] Stack referenciada a playbook existente
  • [ ] Aprovação formal registrada (nome + data) antes de iniciar

Anti-patterns

  • Objetivo vago: "melhorar o processo" — impossível saber quando está pronto
  • Sem escopo OUT: stakeholder espera features que nunca foram prometidas
  • Estimativa sem fases: "2 meses" sem breakdown → impossível detectar atraso cedo
  • Iniciar sem aprovação: trabalho descartado se stakeholder muda de ideia
  • Brief sem métricas de sucesso: projeto entregue mas ninguém sabe se funcionou

5.4 Glossário DELP

Termos específicos do contexto DELP que os agentes NID conhecem e aplicam

Empresa e contexto

DELP — Empresa manufatureira com foco em "Paixão em Fabricar". Opera unidades de produção com controle rigoroso de indicadores.

NID — Núcleo de Inovação DELP. Time responsável por ferramentas de BI, automação, IA e infraestrutura de dados.

ApontDELP — Sistema MES (Manufacturing Execution System) web desenvolvido pelo NID. Stack: Next.js + TypeScript + Prisma + PostgreSQL.

Calendário e tempo

Calendário fiscal DELP — Coincide com calendário civil (jan-dez). Não tem meses fiscais deslocados.

Período DELP — "21 a 20": o período comercial DELP vai do dia 21 de um mês até o dia 20 do mês seguinte (ex: período de março = 21/mar a 20/abr). Isso afeta toda lógica de MTD/YTD nas medidas DAX.

dim_calendario — Tabela de datas padrão NID. Deve ser contínua, sem lacunas, com colunas date, ano, mes, trimestre, periodo_delp, dia_util. Snake_case.

UTC → America/Sao_Paulo — Armazenamento em UTC, exibição em horário de Brasília.

Modelagem e BI

Kimball — Metodologia de modelagem dimensional adotada pelo NID. Tabelas dim_ (dimensões) e fato_ (fatos). PKs surrogadas id_*.

Single-direction — Relacionamentos no Power BI sempre unidirecionais (fato → dim). Bidirecional exige justificativa em ADR.

fato_ — Tabela de fatos: transações, eventos, medições. Ex: fato_producao, fato_vendas.

dim_ — Tabela de dimensão: contexto dos fatos. Ex: dim_produto, dim_colaborador, dim_calendario.

bridge_ — Tabela bridge para relacionamentos M:N.

calculations — Tabela desconectada (disconnected table) que organiza medidas DAX. Hidden no modelo, sem dados reais.

Dados e infraestrutura

SSPI — Security Support Provider Interface (autenticação Windows integrada). Funciona em ambiente on-premise; para Azure, usar Managed Identity.

MI (Managed Identity) — Identidade gerenciada no Azure. Elimina secrets em código. Padrão obrigatório NID para qualquer serviço Azure.

KV (Key Vault) — Azure Key Vault. Armazena secrets, certificados e chaves. Referenciado via MI (sem secret para acessar o KV).

Self-hosted IR — Integration Runtime self-hosted para ADF conectar recursos on-premise (SQL Server, pastas de rede). NID usa ≥2 nós para HA.

RG layout DELP v0 — Grupos de recursos por domínio + env: rg-data-<env>, rg-shared-<env>, rg-network-<env>, rg-bi-<env>, rg-ai-<env>.

IA e Automação

RAG — Retrieval-Augmented Generation. Padrão NID: Azure AI Search + Azure Foundry. Chunk 512/64 tokens.

Claude Agent SDK — SDK da Anthropic para construir agentes autônomos. Stack NID: Python em Azure Functions.

Eval — Suite de avaliação de skills/agentes. Mínimo 5 exemplos golden + métrica quantitativa.

Stop criteria — Condições obrigatórias para parar loop autônomo: max iterações, cost cap, eval-gate.

Processos e nomenclatura

SIT — Solicitação de Informação Técnica. Criada pelo agente quando dado necessário não está disponível no contexto.

ADR — Architecture Decision Record. docs/adr/YYYYMMDD-N-<topico>.md. Obrigatório para override de constituição.

nid-<bucket>-<artefato> — Convenção de nomenclatura de skills. Ex: nid-dax-medidas, nid-azure-bicep-foundations.

Prompt #NNN — Referência ao banco de prompts DELP (pendente — prompts/ em knowledge/). Ex: Prompt #042 — narrativa executiva.

5.5 FAQ — Perguntas frequentes

Respostas para as dúvidas mais comuns ao usar o nid-spec-kit

Sobre instalação e configuração

P: O kit não está reconhecendo as skills. O que fazer?

Verifique se o plugin está registrado:

# Windows: checar config Claude Code
cat "$env:APPDATA\Claude\claude_desktop_config.json"

O bloco nid-spec-kit deve aparecer em plugins. Se não, reexecute .\install.ps1.

P: O hook session-start não está disparando.

Hooks exigem permissão de execução. No Windows, rode Claude Code como administrador na primeira vez, ou adicione permissão manual em ~/.claude/settings.json.

P: Posso usar o kit sem Claude Code CLI (só chat web)?

Sim, mas com limitações: sem ferramentas de arquivo (Read, Edit, Write, Bash), sem hooks, sem subagents reais. Skills e agentes funcionam como persona do LLM — ainda útil para tarefas de chat.

Sobre skills e agentes

P: Qual a diferença entre usar a skill diretamente vs via agente?

  • Skill direta: instrução específica. Bom para tarefa pontual.
  • Via agente: persona completa que usa múltiplas skills automaticamente. Bom para tarefa de domínio complexa.

Prefira agente para tarefas de domínio. Prefira skill direta para consultas rápidas.

P: O agente está dando respostas genéricas sem aplicar as regras NID. Por que?

Causas prováveis:
1. Plugin não carregado → verifique instalação
2. Contexto muito longo → compacte o chat (novos modelos têm compressão automática)
3. Instrução ambígua → seja mais específico: "Use a skill nid-dax-medidas seguindo naming NID"

P: Posso criar minha própria skill?

Sim! Use /nid:skill-create <nome> (após Plan 4) ou copie templates/screen.md manualmente. Siga a convenção nid-<bucket>-<artefato> e adicione ao catálogo em skills/README.md.

Sobre o ciclo SDD

P: Preciso sempre fazer os 5 passos do SDD?

Não em modo Casual. SDD completo é só para projetos Formal com /nid:init. Para tarefas pontuais, use skills/agentes diretamente.

P: O que acontece se eu pular o /nid:gate?

Em projetos Formal, o hook pre-tool-use/block-implement-without-gate bloqueia /nid:implement automaticamente. Para override: "Para esta sessão, pulo o gate formalmente — [justificativa]" (registra em ADR depois).

P: Quanto tempo demora um ciclo SDD completo?

Depende do escopo. Estimativas típicas:
- Feature simples (1 medida DAX): Casual sem SDD, ~15 min
- Feature média (pipeline ETL novo): SDD ~2h (specify 30min + plan 30min + implement 1h)
- Projeto grande (Azure AI + integração): SDD ~2 dias (specify 3h + plan 3h + gate 1h + implement ~1 dia)

Sobre o UniversiNID

P: Este HTML funciona offline?

O conteúdo (texto + navegação) funciona offline. Diagramas Mermaid precisam de internet (CDN). Para uso 100% offline, uma versão futura do build.py com flag --bundle embarcará os scripts.

P: Como faço para abrir como aba no nid-planeta?

<!-- Em qualquer página HTML do nid-planeta: -->
<iframe src="universinid.html" width="100%" height="100%" frameborder="0"></iframe>

Ou como web component (requer que o nid-planeta suporte custom elements):

<nid-universinid src="universinid.html"></nid-universinid>

P: O conteúdo está desatualizado. Como atualizar?

  1. Edite os .md em docs/universinid/
  2. Execute py -3 tools/build_universinid.py
  3. O dist/universinid.html é regenerado
  4. Commite ambos: .md fonte + .html gerado

P: Como reportar problema ou sugerir melhoria?

Reporte no canal NID ou abra issue no GitHub DELP. Para correções rápidas de conteúdo, PR direto é bem-vindo.
